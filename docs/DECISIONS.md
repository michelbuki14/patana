# Decisions (ADRs) — Patana Booking

## ADR-001 — Enums over Free-Text Status Columns

- **Status**: Accepted
- **Context**: Original design used `String` for statuses (`status`, `role`, `propertyType`). Free text allows invalid values, typos, and inconsistent casing; no DB or client validation.
- **Decision**: Define 7 Prisma enums — `UserRole`, `OwnerStatus`, `PropertyType`, `UnitStatus`, `BookingStatus`, `PaymentStatus`, `PaymentMethod` — and use them as column types.
- **Consequences**:
  - Positive: type-safe at Prisma client + DB level, self-documenting, migration-safe renames are explicit.
  - Negative: adding a value requires a migration; slightly more verbose schema.
- **Alternatives considered**: DB `CHECK (status IN (...))` on String columns — works but no Prisma type safety.

## ADR-002 — btree_gist EXCLUDE vs Application Lock for Overlap Prevention

- **Status**: Accepted (defense in depth)
- **Context**: Bookings must not overlap on the same unit for `PENDING`/`CONFIRMED` statuses. App-only checks race under concurrency; DB advisory locks are manual and error-prone.
- **Decision**: Primary guard is Postgres `EXCLUDE USING gist (unitId WITH =, daterange(checkIn, checkOut) WITH &&) WHERE (status IN ('PENDING','CONFIRMED'))` enabled by `btree_gist`. Application layer `canBook()` + `Serializable` transaction is the second layer and the fallback when the extension is unavailable. Migration enables the extension with `CREATE EXTENSION IF NOT EXISTS btree_gist`.
- **Consequences**:
  - Positive: hard DB guarantee even under concurrency; Serializable TX reduces retry surface.
  - Negative: requires `btree_gist` (not available on all managed DBs); GiST index overhead on Booking.
- **Alternatives considered**: `SELECT ... FOR UPDATE` row locks (doesn't work for not-yet-existing overlapping ranges); pure app check (races).

## ADR-003 — Per-Day Availability Rows vs daterange

- **Status**: Accepted
- **Context**: Need to model per-night price overrides and block-out dates. Options: one row per date vs one row with a `daterange` + price.
- **Decision**: One `Availability` row per `(unitId, date)` with `priceOverride Decimal?` and `isAvailable Boolean`. `@@unique([unitId, date])` + `@@index([unitId, date])`.
- **Consequences**:
  - Positive: simple upsert/query (`WHERE unitId=? AND date BETWEEN ? AND ?`), natural for calendar UIs, fine-grained overrides, no range-splitting logic.
  - Negative: more rows (e.g., 365k/yr for 1000 units) — acceptable with indexing; bulk updates need multi-row writes (mitigated by bulk endpoint).
- **Alternatives considered**: `daterange` table (fewer rows but complex merge/split on partial updates, harder to index per-day availability).

## ADR-004 — UUID Primary Keys

- **Status**: Accepted
- **Context**: Choice between auto-increment integers and UUIDs for PKs.
- **Decision**: All tables use `String @id @default(uuid()) @db.Uuid`. Generated by Prisma/DB.
- **Consequences**:
  - Positive: globally unique, safe for distributed generation, no enumeration, stable across merges/sharding.
  - Negative: 16 bytes vs 4, slightly larger indexes, not human-friendly for debugging.
- **Alternatives considered**: `autoincrement Int` (smaller, but leaks count, harder to shard, merge conflicts).

## ADR-005 — Explicit Currency + Idempotency

- **Status**: Accepted
- **Context**: Money handling and payment retries. Implicit currency (assume CDF) is fragile; retries without idempotency risk double-charge.
- **Decision**: (1) Every monetary column paired with `currency String @default("CDF")` on `Booking` and `Payment`, `Decimal(10,2)` for amounts. (2) `Payment.idempotencyKey String? @unique` — clients send `Idempotency-Key` header; server deduplicates on that key.
- **Consequences**:
  - Positive: multi-currency ready, no silent currency mismatch, safe retries.
  - Negative: callers must pass currency; idempotency key storage grows (unique index).
- **Alternatives considered**: App-level currency mapping (no DB column) — rejected as implicit; DB sequence for idempotency — rejected, client-generated UUID is simpler.

## ADR-006 — Modular Monolith + Schema-per-Module + Two-App Frontend

- **Status**: Accepted (authoritative per `patana_architecture.pdf`)
- **Context**: Original codebase was a single-schema Prisma single-service backend (7 tables, one `src/`) with no frontend. Requirements call for an owner-facing and a customer-facing app, clear module boundaries, and independent evolution without paying microservice overhead prematurely.
- **Decision**: (1) **Backend**: NestJS **modular monolith** `patana-api` with 4 modules — `catalog` (Owner, Property, Unit, search), `booking` (Availability + reservations, overlap logic), `checkout` (payments/transactions, idempotencyKey), `shared` (auth/identity User, media Garage S3, notifications, in-process EventBus). Single Postgres, **one Prisma client** with `multiSchema` (`previewFeatures = ["multiSchema"]` + `datasource.schemas = ["public","catalog","booking","checkout","shared"]`, `@@schema("…")` per model). Garage S3 bucket `patana-media` + CDN for media; no DB table for files. (2) **Frontend**: pnpm/npm **monorepo** `patana/` with `apps/customer` (`@patana/customer`) and `apps/owner` (`@patana/owner`) — each React 18 + Vite + TanStack Router/Query/Form + Tailwind/shadcn, own `package.json`. Shared `packages/ui`, `theme`, `api-client` (typed `createClient(baseUrl)`), `types` (UserRole etc.), `validation` (zod schemas) as `workspace:*` deps. (3) **Workspace**: root `package.json workspaces` + `pnpm-workspace.yaml` = `["patana/apps/*","patana/packages/*","patana-api"]`. Legacy `prisma/` + `src/` kept as deprecated pointers to `patana-api/`.
- **Consequences**:
  - Positive: clear bounded contexts (catalog/booking/checkout/shared) without network hop; schema-per-module enables per-module migrations and future service split via outbox; owner vs customer UX can evolve independently; Garage S3 decouples binary storage; EventBus keeps checkout→booking coordination decoupled (swappable to queue later).
  - Negative: `multiSchema` is a Prisma preview feature (requires matching datasource `schemas` + `@@schema` and careful `migrate`); cross-schema FKs still imply single DB coupling; two frontend builds to manage.
- **Alternatives considered**: (a) Keep single schema + single app — rejected, no owner/customer separation, module ownership implicit. (b) Full microservices now — rejected, ops overhead before product-market fit; modular monolith defers that cost while preserving boundaries. (c) Separate Prisma clients per module — rejected, single client is simpler and `multiSchema` already scopes writes.
- **Migration path**: If `multiSchema` is too heavy for an environment, drop `previewFeatures`/`@@schema`/`datasource.schemas` and keep one `public` schema — logical ownership stays per module code (`CatalogModule` still owns Property/Unit). Future split = per-module DB behind outbox + durable queue, Garage S3 unchanged.
